# Exposed webhook signing secret: manual rotation plan

No secret was read or rotated during Phase 28. Treat the previously exposed value as compromised. Keep all payment/observation/release flags OFF. Never paste a new value into chat, a screenshot, a PR, Git, a shell command argument, or an application log.

1. Identify the exact merchant UUID and the correct CredoNomics gateway/consumer environments through an independently authenticated operator session. Do not use the seeded demo merchant or CardLedger database. The current upstream also uses the webhook secret as `X-Merchant-Key`; inventory every server-side consumer, including `YOUPI_MERCHANT_KEY` and `BILLING_YOUPI_WEBHOOK_SECRET`. Neither is publishable.
2. During a separately approved maintenance window, pause webhook dispatch/retries and affected session issuance. Inventory outstanding deliveries using only delivery IDs/payment IDs and reconciliation state; preserve the raw-body evidence in protected storage. Do not blindly replay old SUCCESS deliveries or mark invoices PAID.
3. Generate at least 32 random bytes using a trusted local password/secret manager and store the encoded value directly in that manager. Transfer it through the gateway's authenticated merchant secret configuration and the hosting provider's server-only secret controls, with the key visible only to the authorized operator. This document intentionally provides no command that prints the secret. Those external configuration changes are NOT authorized by Phase 28.
4. Update all intended consumers in a coordinated window. Deployments/restarts needed for changed environment variables require their own approval. Do not keep accepting the exposed old secret as a rotation fallback. Existing retry code signs persisted delivery bodies using the merchant's current key; account for this when resuming the queue.
5. With synthetic bodies and a disposable receiver, verify the new signature, altered raw bytes, absent/old signature rejection, mismatched amount/merchant/order rejection and durable duplicate handling. Verify no headers or tokens are logged. A successful signature establishes message authenticity only.
6. Reconcile pending deliveries against the owning merchant, immutable invoice, exact INR paise, unique payment/event identity and actual independently booked bank credit. COD SUCCESS means order placement, not prepaid funds; counter methods need independently confirmed till evidence. A gateway SMS/Gmail match never automatically issues a CredoNomics PAID receipt.
7. Resume only approved queues after acceptance. Record operator, time, merchant UUID, new secret version identifier and test outcomes in protected audit records, never the secret or its plaintext predecessor. Revoke the old key wherever else it was reused and investigate unauthorized sessions/deliveries since exposure.

Current upstream signs the **raw body only**. Delivery-ID and timestamp headers are not included in the MAC and cannot be used as sole anti-replay evidence. The consumer verifies HMAC before decoding JSON, then records a durable unique payment/event identity and raw-body digest. Contradictory retries become security conflicts. Retries retain the same delivery ID but receive a fresh unsigned timestamp; there is no authenticated timestamp freshness guarantee. No public webhook listener or automatic settlement was enabled by Phase 28.
